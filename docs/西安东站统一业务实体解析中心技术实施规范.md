# 西安东站统一业务实体解析中心技术实施规范

**文档版本：** V1.0\
**适用项目：** 西安东站智慧底座（xian Spring Boot 服务）\
**技术基线：** Java 17、Spring Boot 3.x、Elasticsearch 9.5.6、IK
Analyzer（与 ES 版本严格匹配）、Pinyin Analyzer（与 ES 版本严格匹配）\
**文档状态：** 修订整合版

------------------------------------------------------------------------

## 1. 建设目标

建设统一业务实体解析中心，为西安东站智慧底座中的 Agent、MCP Tool
和业务服务提供统一的实体识别、检索、候选排序与消歧能力。

用户可以使用正式名称、设备编码、简称、现场习惯叫法、中文口语、拼音全拼等方式表达业务对象。系统将自然语言中的实体线索解析为标准业务实体，并返回唯一匹配结果或候选列表，避免
Agent 根据名称自行猜测设备 ID。

### 1.1 首期支持范围

  实体类型   主要数据来源       首期能力
  ---------- ------------------ ------------------------------------------
  区域       AdminClient        标准名称、层级、别名解析
  系统       AdminClient 字典   标准名称、系统编码、别名解析
  设备分类   AdminClient        分类树、标准名称、别名解析
  设备       ScadaClient        编码、名称、别名、区域/系统/分类关联检索
  摄像头     VideoClient        名称、摄像头编号、别名检索

测点、告警、工单等实体可在后续阶段沿用统一接口扩展，不纳入首期强制交付范围。

### 1.2 设计原则

1.  **业务主数据为准，ES 为检索索引。** Admin、Scada、Video
    等源系统是数据权威来源；ES 不作为基础数据的最终权威存储。
2.  **统一入口、独立索引。**
    对外提供统一实体解析能力，设备和摄像头使用独立索引，其他规范实体也可独立建索引。
3.  **先识别实体类型，再执行实体检索。** 设备和摄像头走不同检索链路。
4.  **明确条件先过滤，再做相关性排序。**
    用户明确指定区域、系统或分类时，不允许其他区域/系统的高相似度结果越过硬过滤条件。
5.  **不猜测、不强行唯一化。** 多个候选无法区分时返回 ambiguous，由
    Agent 向用户确认。
6.  **拼音由 ES 分析器处理。** Java
    提交原始中文查询词，不在业务代码中重复生成拼音，不维护手工拼音数组。
7.  **同步幂等、可重试、可对账。**
    全量、增量、手动同步采用统一的数据转换与写入链路。
8.  **首期以词法检索为主。**
    IK、拼音、别名、同义词、模糊查询已能覆盖主要场景，暂不引入向量数据库。

### 2.1 模块职责

建议在 `xian` Spring Boot 工程中增加 `module`
模块，至少划分为以下两个核心子模块：

-   `entity.init`：实体数据初始化与同步服务，负责从源系统获取数据、标准化、关联补全、别名合并、批量写入
    ES。
-   `entity.resolver`：实体解析服务，负责请求标准化、实体类型路由、条件解析、ES
    查询、候选排序、置信度分级和结果返回。

两个模块共享实体模型、索引常量、别名服务和 ES
访问组件，但职责分离。初始化模块不承担用户查询，解析模块不直接调用源系统分页接口。

## 3. 实体标识与别名配置规范

### 3.1 别名配置表

采用一张统一别名配置表，使用 `entity_type`
区分实体类型。别名仅用于检索和解析，不作为前端业务对象的展示名称；展示时始终使用实体的标准名称。

建议表名：`biz_entity_alias`。

  ---------------------------------------------------------------------------------
  字段               类型建议           说明
  ------------------ ------------------ -------------------------------------------
  id                 bigint /           主键
                     varchar(64)        

  entity_type        varchar(32)        AREA、SYSTEM、DEVICE_TYPE、DEVICE、CAMERA

  data_id            varchar(128)       对应实体的稳定业务标识

  alias_name         varchar(255)       别名原文

  normalized_alias   varchar(255)       标准化别名，可用于去重

  enabled            tinyint            是否启用

  source             varchar(32)        MANUAL、SYSTEM、IMPORT 等

  remark             varchar(500)       备注

  created_at         datetime           创建时间

  updated_at         datetime           更新时间
  ---------------------------------------------------------------------------------

建议唯一约束：`(entity_type, data_id, normalized_alias)`。如业务需要同一个别名在不同实体间重复出现，允许跨
`data_id` 重复；解析时保留多候选，不应在数据库层强行认定全局唯一。

### 3.2 data_id 的实体标识映射（本项目约定）

本项目明确采用以下映射，作为别名表与实体索引之间的统一约定：

  实体类型               `data_id` 对应字段   说明
  ---------------------- -------------------- --------------------------------------
  区域 AREA              `cascade_cid`        与其他业务模块使用的区域标识保持一致
  系统 SYSTEM            `element_key`        使用系统字典中的稳定业务编码
  设备分类 DEVICE_TYPE   `id`                 使用设备分类主键
  设备 DEVICE            `id`                 使用设备主键
  摄像头 CAMERA          `id`                 使用摄像头主键

**特别说明：**

-   区域别名的 `data_id` 使用 `cascade_cid`，不改为区域表
    `id`。这是本项目跨业务统一区域标识的明确设计选择。
-   系统别名的 `data_id` 使用 `element_key`，不使用字典记录自身的数据库
    `id`。
-   区域源数据中的 `id`、`parent_id`、`cascade_id`
    等字段仍然保留在区域实体文档中，供层级关系、数据关联和诊断使用；但别名关联键统一使用
    `cascade_cid`。
-   源系统如发生 `cascade_cid` 或 `element_key`
    变更，应作为业务标识变更事件处理：迁移别名关联、更新关联实体文档并执行数据对账，不能静默生成两套实体。

### 3.3 别名管理规则

1.  标准名称不必重复作为别名保存，检索字段本身已包含标准名称。
2.  别名去除首尾空格、统一全半角、统一大小写（适用于英文和拼音），但保留原始
    `alias_name`。
3.  不自动把任意字符串拆成首字母拼音。本项目不建设拼音首字母匹配能力。
4.  别名可配置多个实体类型；例如"空调主机"可能对应多个设备分类或设备候选，不可直接写死为唯一类型。
5.  别名变更后应触发对应实体重新索引，删除别名时同步从 ES 文档中移除。
6.  别名配置必须支持启用/停用、创建人/更新时间审计（如现有系统具备用户审计字段，可沿用现有规范）。

### 3.4 建议 DDL

以下为逻辑参考
DDL，字段长度、主键类型、字符集和审计字段应按现有项目数据库规范调整：

``` sql
CREATE TABLE biz_entity_alias (
    id                BIGINT NOT NULL COMMENT '主键',
    entity_type       VARCHAR(32)  NOT NULL COMMENT 'AREA/SYSTEM/DEVICE_TYPE/DEVICE/CAMERA',
    data_id           VARCHAR(128) NOT NULL COMMENT '实体稳定业务标识',
    alias_name        VARCHAR(255) NOT NULL COMMENT '别名原文',
    normalized_alias  VARCHAR(255) NOT NULL COMMENT '标准化别名',
    enabled           TINYINT NOT NULL DEFAULT 1 COMMENT '是否启用',
    source            VARCHAR(32) DEFAULT 'MANUAL' COMMENT '别名来源',
    remark            VARCHAR(500) DEFAULT NULL COMMENT '备注',
    created_at        DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at        DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_entity_alias (entity_type, data_id, normalized_alias),
    KEY idx_alias_lookup (entity_type, normalized_alias),
    KEY idx_entity_lookup (entity_type, data_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='统一业务实体别名配置表';
```

如果项目主键采用雪花 ID，可由现有 ID 生成器生成
`id`，不要求使用数据库自增。

## 4. 实体模型与 Elasticsearch 索引规划

### 4.1 索引拆分

建议建立以下独立索引：

  索引名称                 实体       说明
  ------------------------ ---------- ---------------------------------------
  `station_areas`          区域       区域标准名称、层级、区域别名
  `station_systems`        系统       系统字典编码、名称、别名
  `station_device_types`   设备分类   分类 ID、名称、父子层级、别名
  `station_devices`        设备       设备主数据及区域/系统/分类冗余信息
  `station_cameras`        摄像头     摄像头名称、编号、NVR、通道等独有字段

设备和摄像头必须使用独立索引。两类数据的来源、字段结构、检索条件及业务语义不同，不应将摄像头字段塞入设备文档，也不应为了统一查询而合并索引。

统一性由 Resolver 和 MCP Tool 提供，不要求底层索引合并。

### 4.2 ES 文档 ID

-   区域：建议使用 `cascade_cid` 作为 ES `_id`。
-   系统：使用 `element_key` 作为 ES `_id`。
-   设备分类：使用分类 `id` 作为 ES `_id`。
-   设备：使用设备 `id` 作为 ES `_id`。
-   摄像头：使用摄像头 `id` 作为 ES `_id`。

使用稳定业务标识作为文档
`_id`，可保证重复同步时覆盖同一文档，实现幂等写入。

### 4.3 区域实体模型

区域源数据来自 AdminClient `/subarea/list`。区域文档建议包含：

``` json
{
  "area_id": "2",
  "cascade_cid": "0.001.001.001-0.001",
  "parent_id": "1",
  "org_id": "3",
  "area_name": "地下层",
  "aliases": ["地下室", "负一层"],
  "parent_name": "西安东站",
  "enabled": true
}
```

区域别名关联 `data_id = cascade_cid`。`area_id`（源数据
`id`）用于保留源系统主键，`cascade_cid` 用于跨业务区域标识和别名关联。

区域层级应同时保留
`parent_id`、`parent_cascade_cid`（如可计算）和完整级联标识。不要只保留展示名称，因为不同楼层或区域可能存在同名。

### 4.4 系统实体模型

系统数据来自 AdminClient 字典接口，首期字典 key 为
`device_system_type`。

``` json
{
  "element_key": "0.001.001",
  "element_value": "智能照明系统",
  "enum_key": "device_system_type",
  "enabled": true,
  "aliases": ["照明", "智能照明"]
}
```

系统别名关联 `data_id = element_key`。检索和设备关联均优先使用
`element_key`，`element_value` 用于展示和文本匹配。

### 4.5 设备分类实体模型

分类数据来自 AdminClient `/base/device/type/list`。

``` json
{
  "device_type_id": "473466096926593025",
  "name": "空调",
  "parent_id": "473466096926593024",
  "cascade_id": "1.001",
  "is_folder": "1",
  "aliases": ["空调设备"]
}
```

设备分类别名关联 `data_id = id`。保留父子关系和
`cascade_id`，支持按分类树检索和上级分类约束。需要区分目录节点与实际设备分类节点，是否允许目录节点作为最终过滤条件由业务规则决定。

### 4.6 设备实体模型

设备数据来自 ScadaClient `/base/device/listPage`。每台设备一个 ES
Document，`_id = device.id`。

``` json
{
  "device_id": "1203022680048013312",
  "org_id": "3",
  "device_name": "地下层冷冻机房排风机1",
  "device_code": "BAS21_PF_N_1_1",
  "device_alias": "BAS21_PF_N_1_1",
  "aliases": ["地下层排风机", "冷冻机房排风机1"],
  "subarea_cid": "0.001.001.001-0.001",
  "subarea_id": "2",
  "subarea_name": "地下层",
  "system_key": "0.001.004",
  "system_name": "暖通系统",
  "device_type_id": "1.005",
  "device_type_name": "风机",
  "parent_device_id": null,
  "enabled": true
}
```

注意：

-   上述字段值仅为结构示例，实际 `device_code`
    应使用源数据中真实、稳定的设备编码字段；如果源数据没有独立编码字段，不要将
    `device_alias` 擅自认定为唯一设备编码。
-   设备文档冗余保存区域名称、系统名称、分类名称，是为了检索和展示效率；关联关系仍使用稳定
    ID/业务编码。
-   `subarea_cid` 与区域实体的 `cascade_cid` 保持一致。
-   `system_key` 对应系统字典 `element_key`。
-   `device_type_id` 对应分类 `id`。
-   对源数据不存在的关联字段允许为空，不要通过名称猜测并写入错误 ID。
-   `parent_device_id` 只有源数据确实提供设备父子关系时才填充。

### 4.7 摄像头实体模型

摄像头数据来自 VideoClient
`/camera/listPage`。用户已确认摄像头没有区域划分，因此首期摄像头模型不建立区域关联字段，不进行区域优先解析，也不以区域作为摄像头过滤条件。

``` json
{
  "camera_id": "1238805390712377344",
  "camera_name": "实验室",
  "camera_no": "34020000001320000532",
  "nvr_id": "1238805016148447232",
  "main_channel": 1,
  "sub_channel": 0,
  "scada_no": 1,
  "org_id": "0",
  "address": "Address",
  "aliases": ["实验室摄像头"],
  "online": true,
  "enabled": true
}
```

摄像头独有字段只保存在 `station_cameras`。摄像头别名关联
`data_id = camera.id`。摄像头数据同步必须遍历分页接口所有页，不能只读取第一页。

## 5. Elasticsearch 分析器与 Mapping 设计

### 5.1 分析器策略

首期采用：

-   IK：中文分词。
-   Pinyin Analyzer：中文转拼音全拼，用于拼音输入检索。
-   Keyword：精确匹配、过滤和排序。
-   Fuzzy：辅助处理少量错别字和英文/编码字符差异。
-   Alias：维护现场简称、口语表达和业务同义词。

**不建设拼音首字母匹配。** 不在 Java 中维护 `pinyin`
数组，也不要求调用方传入 `entity_name_pinyin`。

### 5.2 多字段设计

名称字段采用 multi-fields，为同一原始字段建立多个索引视图：

-   `name`：中文分词字段，使用 IK。
-   `name.raw`：keyword 精确匹配字段。
-   `name.pinyin`：拼音全拼字段，使用 Pinyin Analyzer。

别名字段同样采用中文、精确和拼音子字段。区域名称、系统名称和分类名称按检索需要配置相同策略。

拼音字段由 ES 在索引阶段和查询阶段通过 analyzer 自动处理。Java
只提交原始中文，不额外生成拼音。

### 5.3 Analyzer 配置示例

以下为索引 settings 的设计示例。实际参数名称和插件行为必须以当前安装的
Pinyin 插件版本为准，部署前通过 `_analyze` 验证。

``` json
PUT station_devices_v1
{
  "settings": {
    "analysis": {
      "analyzer": {
        "ik_search": {
          "type": "custom",
          "tokenizer": "ik_max_word"
        },
        "pinyin_full": {
          "tokenizer": "my_pinyin"
        }
      },
      "tokenizer": {
        "my_pinyin": {
          "type": "pinyin",
          "keep_first_letter": false,
          "keep_full_pinyin": true,
          "keep_joined_full_pinyin": true,
          "keep_original": true,
          "limit_first_letter_length": 0,
          "remove_duplicated_term": true
        }
      }
    }
  }
}
```

说明：

1.  `keep_first_letter` 明确关闭，不生成首字母拼音。
2.  `keep_full_pinyin`、`keep_joined_full_pinyin`
    用于全拼检索，具体输出需以插件实际分析结果为准。
3.  `keep_original`
    可保留原始词项，便于混合检索；如分析结果产生冗余，应按真实测试结果调整。
4.  `ik_max_word` 适合索引阶段尽可能细分；查询阶段可结合 `ik_smart` 或
    `ik_max_word` 做对比测试。
5.  不要直接将上述 settings 复制到所有索引而不验证插件版本；应在当前 ES
    9.5.6 环境执行分析测试。

### 5.4 设备 Mapping 示例

``` json
PUT station_devices_v1
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "device_id":       { "type": "keyword" },
      "org_id":          { "type": "keyword" },
      "device_code":     { "type": "keyword" },
      "device_name": {
        "type": "text",
        "analyzer": "ik_max_word",
        "search_analyzer": "ik_smart",
        "fields": {
          "raw":    { "type": "keyword", "ignore_above": 512 },
          "pinyin": { "type": "text", "analyzer": "pinyin_full" }
        }
      },
      "device_alias": {
        "type": "text",
        "analyzer": "ik_max_word",
        "search_analyzer": "ik_smart",
        "fields": {
          "raw":    { "type": "keyword", "ignore_above": 512 },
```

## 6. 数据初始化与同步设计

### 6.1 数据来源

  ---------------------------------------------------------------------------------------------
  数据             来源接口                                          同步方式
  ---------------- ------------------------------------------------- --------------------------
  区域             AdminClient `/subarea/list`                       全量、增量、手动

  系统             AdminClient                                       全量、增量、手动
                   `/enum/getEnumKeyValues?key=device_system_type`   

  分类             AdminClient `/base/device/type/list`              全量、增量、手动

  设备             ScadaClient `/base/device/listPage`               全量分页、增量、单设备

  摄像头           VideoClient `/camera/listPage`                    全量分页、增量、单摄像头
  ---------------------------------------------------------------------------------------------

接口参数、返回结构应以项目实际 Feign Client
定义和源系统实际响应为准。对于分页接口，必须循环拉取所有页，直至达到总数或返回空页。

### 6.2 同步类型

#### 全量同步

适用于首次初始化、数据修复和索引重建。

推荐流程：

1.  创建新版本索引，例如 `station_devices_v2`。
2.  从源系统拉取全量数据。
3.  分批转换、补充关联名称、合并别名。
4.  使用 Bulk API 批量写入。
5.  检查总量、失败数、关键字段和抽样检索。
6.  校验通过后，将读别名从旧索引切换到新索引。
7.  保留旧索引一段时间，确认稳定后再清理。

避免在生产查询过程中直接删除旧索引再重建，降低索引不可用风险。

#### 增量同步

优先使用源系统更新时间、变更日志或消息事件作为增量依据。如果源接口不支持可靠的更新时间过滤，则需要采用定时分页全量对账或按业务可用的变更机制补齐。

增量同步需要覆盖：

-   新增：写入或覆盖对应 `_id`。
-   修改：更新文档及关联名称。
-   删除：删除 ES 文档或标记 `enabled=false`。
-   别名变更：重新生成对应实体文档的 aliases 字段。
-   区域/系统/分类名称变化：更新关联实体文档中的冗余名称字段。

#### 手动同步

提供按实体类型、实体 ID
执行单实体同步的管理接口。单实体同步必须复用全量同步的转换器、别名合并逻辑和写入逻辑，避免出现手动同步与批量同步结果不一致。

### 6.3 同步依赖顺序

推荐顺序：

1.  区域
2.  系统
3.  设备分类
4.  设备
5.  摄像头

设备文档依赖区域、系统、分类的名称补全，因此应先同步规范实体，再同步设备。摄像头独立于区域实体，不依赖区域数据。

### 6.4 Bulk 写入

禁止每条设备数据单独发起一次 ES 请求。使用 Bulk API
分批写入，批次大小通过压测确定，可从 500～1000
条或按请求体大小设置起始值。

每个 Bulk 批次必须检查 item 级错误，不能只判断 HTTP
请求整体成功。失败记录进入重试队列或失败明细表，重试应有次数上限和退避策略。

### 6.5 同步可靠性要求

必须具备：

-   幂等：相同实体重复同步不会产生重复文档。
-   删除同步：源数据删除后 ES 不保留长期脏数据。
-   失败重试：记录失败实体、失败原因、重试次数。
-   并发控制：避免同一实体全量、增量和手动任务同时覆盖。
-   同步状态：记录任务类型、实体类型、开始/结束时间、总量、成功数、失败数。
-   数据对账：源系统总量与 ES 文档数定期核对，并抽样核对关键字段。
-   可观测性：记录 Bulk 耗时、吞吐量、失败率和分页进度。
-   安全切换：全量重建使用新索引和 Alias 原子切换。

### 6.6 建议同步记录

可建立 `biz_entity_sync_task` 和 `biz_entity_sync_error`
两张任务表，或接入现有任务中心。

同步任务至少记录：

`task_id`、`entity_type`、`sync_mode`、`index_name`、`status`、`total_count`、`success_count`、`fail_count`、`started_at`、`finished_at`、`error_message`。

错误明细至少记录：

`task_id`、`entity_type`、`data_id`、`operation`、`error_code`、`error_message`、`retry_count`、`created_at`。

## 7. 实体解析流程

### 7.1 总体流程

``` text
用户输入
   |
   v
请求标准化（去空格、全半角、常见标点规范化）
   |
   v
实体类型识别
   |
   +---------------------------+
   |                           |
   v                           v
设备 DEVICE                摄像头 CAMERA
   |                           |
   v                           v
区域解析（可选）           摄像头索引检索
   |                           |
   v                           |
系统/分类解析（可选）          |
   |                           |
   v                           |
设备索引检索                   |
   |                           |
   +-------------+-------------+
                 |
                 v
            候选排序
                 |
                 v
         置信度与唯一性判断
                 |
        +--------+---------+
        |        |         |
        v        v         v
     matched ambiguous not_found
        |        |         |
        v        v         v
   返回实体   返回候选   提示补充信息
```

### 7.2 实体类型识别

统一解析入口先确定目标实体类型。

可由 Agent 的语义理解结果直接传入 `entity_type`，也可由 Resolver
根据用户表达辅助判断。关键词示例：

-   摄像头：摄像头、监控、视频、画面、打开监控、查看视频等。
-   设备：设备名称、设备编码、冷机、水泵、风机、照明等。

注意：

1.  关键词只用于辅助路由，不应仅凭出现"看一下"等泛化词就认定为摄像头。
2.  用户明确指定 `entity_type` 时，以明确指定为准。
3.  无法可靠判断实体类型时，返回类型候选或要求 Agent
    澄清，不要同时对所有索引进行无约束模糊搜索。
4.  设备与摄像头检索分开执行；不把摄像头当成设备分类或设备文档。

### 7.3 设备解析：先区域，后设备

设备解析采用分层检索，避免直接对全站设备名称做无约束模糊查询。

**第一步：区域解析。**

-   从用户表达中识别区域名称或别名。
-   在 `station_areas` 中检索标准名称、别名、中文分词和拼音全拼。
-   区域别名 `data_id` 使用 `cascade_cid`。
-   唯一命中时，将 `cascade_cid` 作为设备检索过滤条件。
-   多个区域候选时保留候选，必要时要求用户确认。
-   用户没有提及区域，或区域无法解析时，不要强行猜测区域；允许进入全站设备检索。
-   用户明确说了某区域但该区域无法识别时，应提示补充/确认区域，不应静默忽略明确约束并返回其他区域设备。

**第二步：系统和设备分类解析（可选）。**

-   系统从 `station_systems` 解析，关联键为 `element_key`。
-   设备分类从 `station_device_types` 解析，关联键为分类 `id`。
-   大多数自然语言请求可能无法准确提取系统或分类，因此这两个条件都是可选条件。
-   "空调主机"等表达如果可能对应多个分类，不直接映射成一个具体分类；保留多个类型候选，或将其作为名称/别名检索词。
-   只有明确解析成功且无歧义的系统、分类条件，才作为硬过滤条件。

**第三步：设备检索。**

使用 `station_devices`
查询设备名称、设备编码、源设备别名、人工别名，以及区域、系统、分类过滤条件。

如果用户没有提供区域条件，可以全站搜索，但仍需优先精确编码、精确名称、精确别名结果。

### 7.4 摄像头解析

摄像头已确认没有区域划分，因此：

-   不执行区域解析。
-   不使用 `subarea_cid` 作为摄像头过滤条件。
-   直接检索 `station_cameras`。
-   优先匹配摄像头编号 `camera_no`、摄像头名称、别名。
-   可使用
    NVR、通道号等字段作为辅助条件，但只有用户表达中明确包含这些信息时才作为过滤条件。
-   多个摄像头同名或别名相同时返回候选，不强制选取其中一个。

### 7.5 查询标准化

Java 对用户输入执行轻量标准化：

-   去除首尾空格和连续无意义空白。
-   统一全角/半角字符。
-   统一常见连接符和标点。
-   英文字母大小写归一化。
-   对中文数字与阿拉伯数字的等价转换可作为可配置扩展，必须评估误匹配风险。
-   保留原始 query，用于日志、审计和解释。

不要在 Java 中把中文转换成拼音，不要把首字母拼音作为默认召回通道。

## 8. 检索策略与候选排序

### 8.1 查询策略优先级

设备检索建议按以下优先级组合多字段查询：

1.  设备编码精确匹配。
2.  设备名称精确匹配。
3.  设备别名精确匹配。
4.  标准名称 IK 分词匹配。
5.  别名 IK 分词匹配。
6.  名称和别名拼音全拼匹配。
7.  必要时使用 Fuzzy 辅助召回。

摄像头检索采用相同思路，但字段替换为摄像头编号、摄像头名称和摄像头别名。

### 8.2 过滤条件与评分分离

必须将"实体身份匹配"和"业务条件匹配"分开：

-   身份匹配：判断用户说的是哪一个实体，依据编码、名称、别名、分词、拼音等。
-   业务条件：区域、系统、设备分类等明确约束。

明确条件优先作为 filter，而不是简单加分项。例如用户明确指定 B 区，则 A
区设备必须被过滤，不能因名称相似度高而排到前面。

系统和分类只有在明确解析成功时才作为过滤条件；未解析出来时不应默认推断。

### 8.3 评分建议

初期可使用以下业务权重作为排序设计参考，不应直接将其解释为概率：

  匹配维度                            建议参考权重
  ------------------ ----------------------------------------------
  设备编码精确匹配                        100
  设备名称精确匹配                         95
  设备别名精确匹配                         90
  中文分词匹配                     依命中程度动态计算
  拼音全拼匹配                     依命中程度动态计算
  Fuzzy 匹配                      较低权重，仅辅助召回
  区域/系统/分类      作为过滤条件或解释信息，不与身份分数简单相加

最终权重需要用真实设备名称、真实别名和现场用户表达构建测试集后校准。ES
`_score` 是相关性分数，不是 0～100 的概率，也不能直接宣称 96 分就是 96%
置信度。

### 8.4 结果分级

  -----------------------------------------------------------------------------------------
  状态              含义                                         建议处理
  ----------------- -------------------------------------------- --------------------------
  `matched`         唯一候选且置信度达到阈值，业务条件满足       返回标准实体

  `ambiguous`       多个候选相近，或最高候选与次高候选差距不足   返回候选，由 Agent
                                                                 询问用户

  `not_found`       没有可靠候选                                 提示补充名称、编码或区域

  `invalid`         请求参数缺失或实体类型不合法                 返回参数错误
  -----------------------------------------------------------------------------------------

唯一匹配阈值和第一、第二候选分差阈值需经测试集校准。不能仅因 ES
返回第一名就自动认为匹配成功。

### 8.5 候选返回字段

设备候选建议包含：

-   `device_id`
-   `device_name`
-   `device_code`（有值时）
-   `subarea_cid`
-   `subarea_name`
-   `system_key`
-   `system_name`
-   `device_type_id`
-   `device_type_name`
-   `score`
-   `match_reasons`

摄像头候选建议包含：

-   `camera_id`
-   `camera_name`
-   `camera_no`
-   `nvr_id`
-   `main_channel`
-   `sub_channel`
-   `online`
-   `score`
-   `match_reasons`

`match_reasons` 用于解释命中依据，例如
`DEVICE_NAME_EXACT`、`ALIAS_EXACT`、`PINYIN_FULL`、`AREA_FILTER`，便于
Agent 组织自然语言确认。

## 9. MCP Tool 设计

### 9.1 对外统一 Tool

向 Hermes / Agent 暴露一个统一 Tool：

`resolve_business_entity`

内部根据 `entity_type` 路由到不同
Resolver。对外统一不意味着底层设备和摄像头共用索引。

### 9.2 请求参数

建议参数结构：

``` json
{
  "entity_type": "device",
  "query": "查一下B区那个2号冷机",
  "filters": {
    "area_name": "B区",
    "area_cascade_cid": null,
    "system_name": null,
    "system_key": null,
    "device_type_name": null,
    "device_type_id": null
  },
  "top_k": 5
}
```

摄像头请求示例：

``` json
{
  "entity_type": "camera",
  "query": "打开实验室监控",
  "filters": {},
  "top_k": 5
}
```

参数约定：

-   `entity_type`：必填，建议枚举
    `device`、`camera`、`area`、`system`、`device_type`。
-   `query`：必填，用户原始表达或提取后的实体名称。
-   `filters`：可选，Agent 已明确识别的业务过滤条件。
-   `top_k`：可选，默认 5，设置合理上限，例如 20。
-   不提供 `entity_name_pinyin`，不要求 Agent 或 Java 生成拼音。

如果 Agent 已经从原始自然语言中提取出名称和区域，可在请求中传入更明确的
query 与 filters；Resolver 仍应保留原始表达用于日志和结果解释。

### 9.3 返回结构

``` json
{
  "status": "ambiguous",
  "entity_type": "device",
  "resolved": null,
  "candidates": [
    {
      "entity_id": "CH-002",
      "name": "2号冷水机组",
      "area_name": "B区",
      "system_name": "中央空调系统",
      "device_type_name": "冷水机组",
      "score": 12.8,
      "match_reasons": ["DEVICE_NAME_TOKEN", "AREA_FILTER"]
    },
    {
      "entity_id": "CH-003",
      "name": "3号冷水机组",
      "area_name": "B区",
      "system_name": "中央空调系统",
      "device_type_name": "冷水机组",
      "score": 10.6,
      "match_reasons": ["DEVICE_TYPE_TOKEN", "AREA_FILTER"]
    }
  ],
  "reason": "B区存在多个符合条件的冷水机组，请用户确认具体设备。",
  "matched_filters": {
    "area": "B区"
  }
}
```

分数示例仅用于说明字段，不代表实际 ES 分值或概率。

### 9.4 Java 返回对象建议

``` java
@Data
public class EntityResolveResult<T> {
    /** matched / ambiguous / not_found / invalid */
    private String status;

    /** device / camera / area / system / device_type */
    private String entityType;

    /** 唯一匹配实体 */
    private T resolved;

    /** 候选列表 */
    private List<EntityCandidate<T>> candidates;

    /** 匹配说明 */
    private String reason;

    /** 实际生效的过滤条件 */
    private Map<String, Object> matchedFilters;
}
```

``` java
@Data
public class EntityCandidate<T> {
    private T entity;
    private double score;
    private List<String> matchReasons;
}
```

MCP Tool 返回应控制字段体积，不返回无关源系统大字段、摄像头复杂参数 JSON
或设备全量属性。

## 10. Java 服务设计

### 10.1 核心服务职责

建议核心服务如下：

  服务                      职责
  ------------------------- ----------------------------------
  `EntityResolverService`   统一入口、实体类型路由、结果封装
  `QueryNormalizer`         查询文本标准化
  `EntityTypeDetector`      设备/摄像头等实体类型识别辅助
  `AreaResolver`            区域解析
  `SystemResolver`          系统解析
  `DeviceTypeResolver`      设备分类解析
  `DeviceResolver`          设备检索
  `CameraResolver`          摄像头检索
  `EntityQueryBuilder`      统一构建 ES 查询条件
  `CandidateRanker`         候选排序、分差和阈值判断
  `EntityAliasService`      别名读取、维护和缓存
  `EntityIndexService`      ES 索引读写、Bulk、Alias 管理

### 10.2 统一解析伪代码

``` java
public EntityResolveResult<?> resolve(ResolveEntityRequest request) {
    validate(request);

    String query = queryNormalizer.normalize(request.getQuery());
    String entityType = resolveEntityType(request);

    return switch (entityType) {
        case "device" -> {
            AreaResolveResult area = areaResolver.resolveIfMentioned(query, request.getFilters());
            validateAreaAmbiguity(area);

            ResolvedFilters filters =
                filterResolver.resolveOptionalSystemAndType(query, request.getFilters());

            yield deviceResolver.resolve(query, area, filters, request.getTopK());
        }
        case "camera" -> cameraResolver.resolve(query, request.getFilters(), request.getTopK());
        case "area" -> areaResolver.resolve(query, request.getTopK());
        case "system" -> systemResolver.resolve(query, request.getTopK());
        case "device_type" -> deviceTypeResolver.resolve(query, request.getTopK());
        default -> EntityResolveResult.invalid("不支持的实体类型");
    };
}
```

该代码为职责示意，实际实现需结合项目使用的 Elasticsearch Java Client
版本、MCP 框架和现有异常处理规范。

### 10.3 ES 查询构造建议

设备查询应将明确条件放入 `bool.filter`，将名称、别名和拼音检索放入
`bool.should`，并设置合理的 `minimum_should_match`。

示意结构：

``` json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "enabled": true } },
        { "term": { "subarea_cid": "0.001.001.001-0.001" } }
      ],
      "should": [
        { "term": { "device_code": { "value": "BAS21_PF_N_1_1", "boost": 100 } } },
        { "term": { "device_name.raw": { "value": "2号冷水机组", "boost": 95 } } },
        { "term": { "aliases.raw": { "value": "2号冷机", "boost": 90 } } },
        { "match": { "device_name": { "query": "2号冷机", "boost": 8 } } },
        { "match": { "aliases": { "query": "2号冷机", "boost": 7 } } },
        { "match": { "device_name.pinyin": { "query": "2号冷机", "boost": 5 } } },
        { "match": { "aliases.pinyin": { "query": "2号冷机", "boost": 4 } } }
      ],
      "minimum_should_match": 1
    }
  },
  "size": 5
}
```

实际代码需补齐 JSON 括号并根据客户端 DSL
构造。示例仅表达查询结构：精确匹配、中文分词、拼音召回分别设置权重；明确区域条件在
filter 中。

如果用户没有明确区域，则不添加区域
filter。系统和分类同理：只有明确解析成功时才添加。

## 12. Elasticsearch 部署与安全注意事项

### 12.1 版本

当前项目已部署 Elasticsearch 9.5.6 和 IK 分词器。后续安装 Pinyin
Analyzer 时必须选择与 ES 9.5.6 兼容的插件构建，并在测试环境验证。

Elasticsearch、Kibana
和分析插件尽量保持同一兼容版本。升级前先备份数据并验证索引兼容性。

### 12.2 插件安装路径

原部署操作中存在文件复制路径与安装路径不一致的问题：复制到容器的
`/opt/...`，安装命令却从 `/tmp/...`
读取。安装命令必须指向容器内实际存在的 zip 路径。

建议使用一致路径，例如：

``` bash
docker cp elasticsearch-analysis-ik-9.5.6.zip es9:/tmp/elasticsearch-analysis-ik-9.5.6.zip
docker exec -u 0 -it es9 \
  /usr/share/elasticsearch/bin/elasticsearch-plugin install --batch \
  file:///tmp/elasticsearch-analysis-ik-9.5.6.zip
```

Pinyin 插件采用相同方式安装，并确认插件列表：

``` bash
docker exec es9 \
  /usr/share/elasticsearch/bin/elasticsearch-plugin list
```

插件安装后通常需要重启 Elasticsearch 容器，重启前应确认数据目录持久化。

### 12.3 镜像地址

Elasticsearch 镜像应使用 Elasticsearch 官方镜像，例如：

``` text
docker.elastic.co/elasticsearch/elasticsearch:9.5.6
```

Kibana 镜像：

``` text
docker.elastic.co/kibana/kibana:9.5.6
```

`docker.elastic.co/r/elastic-agent` 是 Elastic Agent 相关镜像地址，不是
Elasticsearch 服务镜像，不应作为 ES 容器镜像使用。

### 12.4 数据卷

数据目录和插件目录可持久化挂载。挂载整个 `config`
目录前，应确认宿主机目录包含完整且正确的配置文件，否则可能覆盖容器默认配置并导致
ES 无法启动。优先采用必要文件级挂载或经过验证的完整配置目录。

### 12.5 账号密码

禁止在代码、Markdown 文档、Git 仓库、部署脚本中明文保存 ES
账号密码。当前环境中曾出现默认弱密码配置，应立即更换为强密码，并通过环境变量、配置中心或密钥管理方式注入。

生产环境应：

-   开启并正确配置 HTTPS/TLS。
-   限制 9200 端口的网络访问范围。
-   应用账号遵循最小权限，只授予所需索引的读写权限。
-   不使用 `elastic` 超级管理员账号作为应用连接账号。
-   定期轮换凭据并审计访问日志。

## 13. 性能与容量建议

1.  ES 仅存储检索所需字段及必要展示字段，不复制设备全部业务属性。
2.  设备和摄像头独立索引，避免不同数据类型混合造成 mapping 膨胀。
3.  使用 Bulk 写入和合理批次，避免单条写入。
4.  查询默认返回 Top 5，允许调用方设置上限，避免一次返回大量候选。
5.  仅对名称、别名、编码、区域、系统、分类等检索相关字段建立索引。
6.  不需要对所有字段建立拼音子字段；只对用户可能输入检索的中文名称类字段建立。
7.  对高频规范实体和别名可使用本地缓存或 Redis
    缓存，但缓存失效必须由别名变更和实体同步事件触发。
8.  首期不引入向量数据库。IK、Pinyin、别名、同义词和 Fuzzy
    属于词法/模糊检索能力，不等同于向量语义检索；后续如出现复杂描述型语义检索需求，再评估
    embedding 与向量召回。

## 14. 日志、监控与异常处理

### 14.1 解析日志

每次解析至少记录：

-   request_id / trace_id
-   entity_type
-   原始 query（按项目数据安全规范脱敏）
-   标准化 query
-   生效过滤条件
-   命中的索引
-   候选数量
-   最终 status
-   Top 候选 ID 与命中原因
-   ES 查询耗时
-   总耗时

### 14.2 同步监控

监控：

-   各实体源数据总量和 ES 文档数。
-   全量/增量同步耗时。
-   Bulk 吞吐量、失败数和重试数。
-   分页同步进度。
-   别名数据量和异常关联数。
-   索引 Alias 指向和索引健康状态。

### 14.3 异常策略

-   源系统接口不可用：任务标记失败或部分失败，不得将空数据误判为全量删除。
-   ES 不可用：同步任务保留失败记录，恢复后可重试。
-   单条数据格式错误：记录错误实体并继续处理其他记录，避免整批中断。
-   别名关联不到实体：进入异常数据列表，不静默丢弃。
-   查询超时：返回可识别的服务异常状态，不将其伪装成 `not_found`。
-   索引 mapping 不兼容：停止写入并报警，禁止自动删除索引解决。

## 15. 测试与验收标准

### 15.1 数据初始化验收

-   区域、系统、分类、设备、摄像头均完成首次全量同步。
-   摄像头分页接口遍历所有页，文档数与源接口总数核对。
-   设备文档能够正确关联区域 `cascade_cid`、系统 `element_key`、分类
    `id`。
-   摄像头模型不包含区域关联逻辑。
-   同一实体重复同步不会产生重复文档。
-   源数据删除、别名删除和名称变更能够同步反映到 ES。
-   Bulk 部分失败可定位、可重试。
-   全量重建可通过 Alias 安全切换。

### 15.2 检索验收用例

  场景              输入示例                  预期
  ----------------- ------------------------- ------------------------------
  设备标准名称      `地下层冷冻机房排风机1`   命中对应设备
  设备源别名/编码   `BAS21_PF_N_1_1`          精确命中对应设备
  设备现场简称      `地下层排风机`            通过别名命中
  区域别名          `地下室的排风机`          先解析区域，再检索设备
  区域未提及        `查一下2号冷机`           允许全站检索，不猜测区域
  区域多义          存在多个同名区域          保留候选并澄清
  明确区域不匹配    `B区2号冷机`              不返回 A 区设备作为有效匹配
  系统未提及        `查一下排风机`            不强制推断系统
  分类多义          `空调主机`                不强行映射唯一分类
  拼音全拼          `lengshuijizu`            可通过全拼字段召回
  首字母拼音        `lsjz`                    不作为系统保证支持的检索方式
  摄像头名称        `实验室监控`              走摄像头独立索引
  摄像头编号        `34020000001320000532`    精确命中摄像头
  摄像头区域表达    `打开实验室监控`          不执行区域解析
  多候选            多台设备别名相同          返回 ambiguous
  无匹配            不存在的设备名称          返回 not_found

### 15.3 性能验收

建议使用实际生产规模数据构建压测集，覆盖：

-   设备名称精确匹配。
-   别名匹配。
-   IK 分词匹配。
-   拼音全拼匹配。
-   区域过滤后的检索。
-   无区域全站检索。
-   摄像头名称与编号检索。
-   并发查询和批量同步同时运行。

响应时间目标应结合部署服务器 CPU、内存、磁盘、ES
JVM、数据规模和并发量实测后确定，不在未压测前承诺固定毫秒数。

## 17. 最终技术决策汇总

  事项                   最终决策
  ---------------------- -----------------------------------------
  统一解析入口           `resolve_business_entity`
  设备与摄像头索引       独立索引
  区域别名 `data_id`     `cascade_cid`
  系统别名 `data_id`     `element_key`
  分类别名 `data_id`     分类 `id`
  设备别名 `data_id`     设备 `id`
  摄像头别名 `data_id`   摄像头 `id`
  摄像头区域             确认没有区域划分，不做区域解析和过滤
  拼音                   ES Pinyin Analyzer 处理全拼
  拼音首字母             不建设、不保证支持
  Java 拼音转换          不做
  名称字段               IK + keyword 精确 + Pinyin multi-fields
  别名检索               与标准名称一起进入检索
  明确区域/系统/分类     作为硬过滤条件
  未解析的系统/分类      不强制猜测
  区域未提及             允许全站检索
  评分                   相关性排序，不等于概率
  多候选                 返回 ambiguous，由 Agent 澄清
  数据写入               Bulk
  全量重建               新索引校验后 Alias 切换
  同步机制               全量 + 增量 + 手动单实体
  向量数据库             首期不引入

**实施结论：** 按本规范建设统一业务实体解析中心。对外统一
Tool，对内按实体类型拆分 Resolver
和索引；以源系统主数据为准，以统一别名表扩展现场表达，以 Elasticsearch
完成中文分词、拼音全拼和模糊召回，以明确业务条件过滤和候选消歧保证实体识别的准确性。
